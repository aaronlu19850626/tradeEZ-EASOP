# TradeEZ-SOP 第八项：交易请求结果闭环设计

> 状态：P8-D01 至 P8-D10 已确认；代码实现与编译完成，等待模拟账户专项验证  
> 范围：开仓、挂单、改单、撤单、全平、策略平仓、盈利单平仓、动态退出和趋势部分平仓

## 1. 本项目标

所有交易动作都从“调用函数”升级为“可追踪操作”：记录意图、请求ID、服务器响应、成交结果、实际剩余仓位以及最终状态。界面和日志只能在服务器事实已经满足目标时显示“完成”，不能再把“请求已发送”写成“已经平仓”或“已经减仓”。

MetaQuotes官方说明：`OrderSendAsync()` 返回成功只表示请求已经发送，不保证服务器接受或成交；一次请求会产生多条且顺序不保证的交易事务，应使用 `request_id` 关联 `TRADE_TRANSACTION_REQUEST`，并最终核对订单、持仓和成交池。参考：[OrderSendAsync](https://www.mql5.com/en/docs/trading/ordersendasync)、[OnTradeTransaction](https://www.mql5.com/en/docs/event_handlers/ontradetransaction)、[MqlTradeResult](https://www.mql5.com/en/docs/constants/structures/mqltraderesult)。

## 2. 当前实现审计

| 编号 | 当前行为 | 风险 |
|---:|---|---|
| P8-01 | 批量平仓使用 `OrderSendAsync()` 连续发送，只返回 submitted 数量 | submitted不等于接受或成交，残仓没有统一收口 |
| P8-02 | 批量撤单只判断异步调用布尔值 | 挂单可能仍留在服务器 |
| P8-03 | 护城河调用全平后立即设置 `g_MoatLiquidated=true` 并提示“已平仓” | 服务器拒绝或部分成交时，状态和真实风险相反 |
| P8-04 | 趋势部分平仓在 `PositionClosePartial()` 返回true后立即标记已减仓 | 部分成交、拒绝或实际剩余量不符时永久跳过减仓 |
| P8-05 | 趋势峰值回撤直接调用 `PositionClose()`，没有退出中状态 | 每Tick重复或失败后无清晰告警 |
| P8-06 | 同步 `OrderSend`/CTrade成功也被当作动作完成 | 官方说明同步返回同样不保证最终成交 |
| P8-07 | `OnTradeTransaction()`只刷新保护、状态和风控 | 没有处理`TRADE_TRANSACTION_REQUEST`，也没有使用`request_id` |
| P8-08 | 没有统一操作ID和批次ID | 无法把多条事务归属到一次用户操作 |
| P8-09 | 重启后没有未完成请求恢复 | 可能丢失退出、撤单和减仓意图 |
| P8-10 | 同一按钮可在前一请求未完成时再次触发 | 可能产生重复开仓、重复减仓或请求风暴 |

## 3. 统一请求账本

建立独立原子文件 `TradeEZ/requests/v1/...csv`，不与逐票策略V5混写。每条操作至少保存：

- `operation_id`：EA生成的单调唯一ID；
- `batch_id`：一次批量操作下所有子请求共享；
- `action`：开仓、挂单、改单、撤单、全平、部分平仓；
- `source`：用户按钮、剥头皮回撤、趋势回撤、超时、保护失败、护城河等；
- `target_ticket`、`position_id`、symbol、magic；
- 请求量、目标剩余量、请求价格/SL/TP；
- `request_id`、order、deal、retcode、external retcode；
- 创建、提交、服务器响应、最后核对和完成时间；
- 尝试次数、下次重试时间和最后错误；
- 状态与最终说明。

文件使用临时文件加原子替换；未完成记录立即保存，完成记录保留7天用于审计。账户、服务器、品种和实例继续进入命名空间。

## 4. 操作状态机

| 状态 | 含义 |
|---|---|
| `CREATED` | 意图已持久化，尚未发送 |
| `SUBMITTED` | 本地已发送，等待服务器请求结果 |
| `ACCEPTED` | 服务器接受，等待订单/成交/持仓事实收敛 |
| `PARTIAL` | 已有部分结果，但尚未达到目标 |
| `CONFIRMED` | 服务器事实满足目标 |
| `FAILED` | 明确拒绝或重试策略耗尽，需要用户处理 |
| `AMBIGUOUS` | 重启或事件缺失，无法安全判断是否执行 |
| `CANCELLED` | 发送前被用户或更高优先级规则取消 |

状态只能向结果方向前进；收到事务事件只作为线索，最终以当前订单/持仓池及成交历史核对为准。

## 5. 请求关联与事件处理

1. 发送前先创建并原子保存账本记录。
2. 使用原始 `MqlTradeRequest/MqlTradeResult` 或CTrade的请求结果保存终端 `request_id`。
3. `OnTradeTransaction()`仅在 `TRADE_TRANSACTION_REQUEST` 时读取request/result并按 `request_id`更新服务器响应；其他事务只记录受影响ticket并设置“需要核对”标志。
4. 事件处理器不得执行历史大扫描、弹窗或长循环，避免占满官方1024条事务队列。
5. 1秒安全时钟统一执行仓位、挂单和成交核对，再更新最终状态、风险和界面。

## 6. 不同操作的完成判定

| 操作 | `CONFIRMED`标准 |
|---|---|
| 市价开仓 | 找到与操作关联的成交和新持仓，实际手数符合允许范围，服务器SL/TP通过保护审计 |
| 限价挂单 | 服务器活动订单存在，票号、方向、价格、手数、SL/TP均符合请求 |
| 修改SL/TP | 回读服务器仓位/订单，目标保护已达到或比目标更安全 |
| 撤单 | 指定order ticket不再位于活动订单池，且历史状态可解释为取消或已成交 |
| 全平 | 指定position ticket已消失；部分成交时进入`PARTIAL`并更新剩余量 |
| 部分平仓 | 当前剩余手数达到目标剩余量；只按差额继续处理 |

订单因TP/SL先成交、用户手工处理或券商操作而提前满足目标时，也可标记`CONFIRMED`，但final reason必须记录外部完成来源。

## 7. 重试与防重复

### 7.1 退出、撤单、修改

- 每次重试前先核对目标是否已经满足；满足则不再发送。
- 快速重试节奏为1、2、4、8秒。
- 强制退出类在快速重试后仍未完成，进入慢速15秒重试并持续醒目告警，只要仓位仍在就不宣称完成。
- 部分平仓每次只请求“当前手数−目标剩余手数”，禁止重复使用原始减仓量。

### 7.2 新增风险

- 市价开仓或新挂单处于`SUBMITTED/ACCEPTED/AMBIGUOUS`时，禁止相同按钮再次发送。
- 对结果不明确的新增风险不自动重试，先核对服务器和历史；仍无法证明时进入`AMBIGUOUS`，由用户确认后再操作。
- 这是为了避免网络抖动或重启造成双倍开仓。

## 8. 批量操作

### 8.1 手动一键全平/平策略/平盈利单

- 点击时建立目标快照和一个batch，每个ticket一条子操作。
- 所有子请求继续使用异步扇出，一次性快速发送，不逐单等待。
- “一键全平”同时快照当前品种所有持仓和挂单，并弹出一次确认，显示数量和范围。
- 批次只有在全部子操作`CONFIRMED`后才显示“完成”；否则显示完成数、处理中数和失败数。
- 点击后新产生的外部订单不自动纳入该手动批次，避免超出用户确认范围。

### 8.2 护城河和风险强平

- 风控清盘是持续目标，不是一次快照：在锁定状态期间持续发现并纳入当前品种新出现的持仓/挂单，直到真实空仓空单。
- `g_MoatLiquidated`只代表“清盘锁已触发”，界面分别显示“清盘中”和“已清盘”。
- 任何残仓或挂单存在时不得显示“已平仓”。

## 9. 与现有状态机衔接

- 剥头皮`EXIT_PENDING`把关闭动作委托给统一账本；仓位消失后才转`CLOSED`。
- 趋势增加退出中状态，回撤触发后不再每Tick直接平仓。
- `g_TrReduced=true`只能在实际剩余手数达到目标后设置。
- 第五项保护修复仍保留安全线，但发送、回执和最终复核进入同一账本。
- 第七项`TP_REMOVE_PENDING`通过账本核销，服务器确认TP为零后才转`TP_REMOVED`。
- 第九项统一风险计算将直接把未完成的新增风险请求纳入额度；本项先提供可靠账本数据。

## 10. 界面与提示

- 交易按钮提交后显示处理中或禁用，直到相应操作进入终态。
- 批量平仓显示`已完成/总数`，失败时显示残留ticket和简明原因。
- 成功提示使用“服务器已确认”；发送阶段只使用“请求已提交”。
- 专家日志统一包含operation_id、batch_id、request_id、ticket、attempt、retcode和最终状态。
- 不对每条事务弹窗；只在批次最终完成、明确失败或需要用户决定时提示。

## 11. 重启恢复

1. 加载未完成账本；
2. 先核对当前持仓、挂单及最近成交历史；
3. 已满足目标的操作补记`CONFIRMED`；
4. 退出、撤单和保护修改可按剩余目标继续；
5. 新增风险结果不明确时标记`AMBIGUOUS`，禁止自动重发；
6. 恢复完成前禁止新增交易，但允许用户执行更低风险的平仓动作。
