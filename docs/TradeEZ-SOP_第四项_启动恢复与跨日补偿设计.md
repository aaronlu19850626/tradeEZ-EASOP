# TradeEZ-SOP 第 4 项：启动恢复与跨日补偿设计

> 状态：P4-D01 至 P4-D10 已全部确认，专项运行验证通过并完成交付  
> 日期：2026-09-19（北京时间）  
> 本阶段先冻结恢复口径、失败策略和验收标准；确认后再修改交易代码。

## 1. 目标与边界

第四项解决三类问题：

1. EA 或 MT5 在每日重置时刻未运行，重新启动后仍能幂等补做日初始化；
2. 当日纪律状态缺失或过期时，尽量从账户成交历史精确重建；
3. 第三项发现的逐票状态缺失或身份不匹配时，执行明确、可审计的保守接管。

本项不承诺恢复终端关闭期间真实经历过的浮盈峰值。没有持续运行的 EA 就没有完整 Tick 路径；仅凭重启时价格不能证明离线期间是否先大幅盈利后回撤。服务器固定保护将在第 5 项加强。

## 2. 当前实现的主要问题

### 2.1 启动顺序掩盖漏跑

当前 `OnInit()` 先把 `g_DayStart` 设置为当前统计日，再读取持久化状态。若保存的是上一交易日，读取直接失败并按“全新一天”初始化：

- 不知道错过了几个重置点；
- 不补导出上一交易日报告；
- 没有恢复审计记录；
- 无法区分首次安装、正常跨日和异常断档。

### 2.2 日初始化不是独立事务

当前跨日逻辑依赖 Tick 或风控检查触发，且“导出旧日、清空状态、建立新基线、写入完成标志”没有事务编号。中途终止可能重复导出或只完成一半。

### 2.3 可重建状态与不可重建状态混在一起

以下状态可从完整成交历史精确重建：

- 当日已实现盈亏及胜负统计；
- 剥头皮、趋势、全部订单的已实现累计峰值；
- 连续亏损序列；
- 自然周已实现盈亏和周目标进度。

以下状态只能从最近检查点延续，不能靠当前价格精确补回：

- 离线期间的浮盈最高点；
- 离线期间动态追踪本应移动到的最高止损；
- 没有记录时，用户是否曾手动取消超时平仓或执行“改趋势”；
- 没有完整 Tick 历史时，持仓在离线区间的真实路径。

### 2.4 连亏游标精度不足

当前仅保存秒级 `g_LastDealTime`，并用 `dtime <= g_LastDealTime` 去重。同一秒出现多笔平仓时，重启或多次扫描可能漏计。恢复游标需要升级为：

```text
DEAL_TIME_MSC + deal_ticket
```

并按这两个字段稳定排序。

### 2.5 历史不可用时仍可能开放交易

若 `HistorySelect()` 失败或历史尚未下载完成，当前函数多以零值返回。零值会被误认为“今天没有亏损”，导致风控在信息不完整时错误放行。

## 3. 恢复状态机

新增恢复阶段：

| 状态 | 含义 | 允许操作 |
|---|---|---|
| `RECOVERY_CHECKING` | 正在读取检查点、成交历史和逐票状态 | 仅查看、仅平仓 |
| `RECOVERY_EXACT` | 当前统计日关键状态可精确恢复 | 正常运行 |
| `RECOVERY_CONSERVATIVE` | 存在无法精确还原的逐票或浮盈路径 | 允许管理/平仓，禁止新开仓，等待用户确认 |
| `RECOVERY_FAILED` | 历史缺失、文件损坏或时间基准不可信 | 仅平仓，禁止开仓与自动推断 |

面板顶部显示一次性恢复结论，专家日志写出恢复来源、断档时长、处理票数和不确定项。不得用零值静默代替失败。

## 4. 启动恢复顺序

主实例取得租约后按以下固定顺序执行：

1. 获取可靠当前时间和当前统计周期；
2. 读取“最后完成统计周期”和恢复检查点，不立即覆盖；
3. 检查成交历史是否覆盖需要恢复的时间范围；
4. 若跨过重置点，按日期顺序补做遗漏周期；
5. 从当日成交历史重建已实现统计、连亏序列和精确高水位；
6. 恢复第三项逐票状态；缺失状态进入保守接管；
7. 重新计算当前浮动盈亏与当前已知净值；
8. 先保存完整新检查点，再将恢复状态切换为可交易；
9. 最后启动 Tick 管理、风控和界面交易入口。

恢复未完成前，任何按钮、定时器或 Tick 都不能新增风险。

## 5. 幂等跨日事务

每个统计周期使用稳定 ID：

```text
period_id = 北京时间重置时刻对应的 YYYYMMDD-HHMM
```

持久化以下标志：

```text
last_completed_period
last_reported_period
recovery_started_utc
recovery_completed_utc
recovery_result
```

补做顺序：

1. 读取上一周期的历史区间；
2. 以明确的起止时间生成报告，文件名固定；
3. 原子写报告，重复运行覆盖同一周期文件，不产生重复文件；
4. 建立新周期基线；
5. 保存新周期状态；
6. 最后更新 `last_completed_period`。

若在第 2 至第 5 步中断，下次启动仍从同一周期重新执行，结果保持一致。

## 6. 当日状态重建

### 6.1 精确重建

按 `DEAL_TIME_MSC, deal_ticket` 升序扫描当前统计周期的出场成交：

- 重建全部、剥头皮和趋势已实现盈亏；
- 重建各口径的累计已实现盈利峰值；
- 重放连续亏损状态机和冷却触发时间；
- 保存毫秒成交游标，避免同秒漏单；
- 周进度继续按北京时间自然周一 00:00 至当前时刻直接扫描历史，不依赖某次日初始化是否运行。

### 6.2 已知下界恢复

全局净盈利高水位采用：

```text
max(同日有效检查点高水位, 历史已实现累计峰值, 当前净盈亏)
```

它是“已知下界”，不是离线浮盈峰值的证明。若离线区间存在持仓，则恢复结果标记为 `RECOVERY_CONSERVATIVE`，明确提示离线峰值不可验证。

### 6.3 初始余额

沿用当前产品口径：

```text
当前余额 - 当前统计周期内本品种全部已实现盈亏
```

入金、出金、其他品种交易以及跨日持仓的严格权益切片将在第 9/10 项统一风险与日统计口径中处理；第四项不悄然改变现有产品定义。

## 7. 缺失逐票状态的保守接管

对第三项标记为缺失或身份不匹配的当前持仓：

1. 仅使用可验证的 symbol、magic、position identifier、开仓时间和当前 SL/TP；
2. 不推断曾经的历史峰值；恢复峰值只从当前浮盈点数开始；
3. 趋势单剩余手数低于标准手数时可判定“可能已减仓”，为防重复减仓按“已减仓”处理；手数无法判断时仅禁用再次减仓；
4. 剥头皮单 TP 已被清除时，不自动补回 TP，也不宣称它一定执行过“改趋势”；
5. 已超过超时期限的未知剥头皮单不在启动瞬间强平，先标记为人工确认，避免恢复动作造成意外平仓；
6. 这些持仓继续允许用户主动平仓，但在用户确认恢复摘要前禁止新增仓位；
7. 用户确认只代表接受保守接管结果，不代表系统已经还原离线峰值。

## 8. 历史数据完整性门槛

启动时必须验证：

- `HistorySelect()` 成功；
- 最早可用历史覆盖当前统计日起点；
- 所有读取到的成交字段合法；
- 服务器时间、GMT 与北京时间换算结果合理；
- 同一成交游标重放两次结果一致。

历史尚未下载或选择失败时进入 `RECOVERY_FAILED`。系统可以继续展示报价和执行平仓，但禁止开仓；定时重试历史恢复，成功后自动重新评估。

## 9. 漏跑报告范围

为避免用户数月未启动后一次性扫描无限历史，建议：

- 自动补做最近 31 个统计周期的报告；
- 超过 31 天的缺口只记录审计摘要，不自动批量导出；
- 当前统计周期始终恢复，不受 31 天限制；
- 报告按固定周期文件名幂等覆盖。

## 10. 验收场景

| ID | 场景 | 通过条件 |
|---|---|---|
| P4-01 | 同一统计日正常重启 | 检查点和历史合并后状态不倒退 |
| P4-02 | 关闭期间跨过一个重置点 | 启动时补做一次旧日报告并建立新日状态 |
| P4-03 | 关闭期间跨过多个重置点 | 按日期顺序幂等补做，最多自动处理 31 天 |
| P4-04 | 补做过程中再次中断 | 下次启动重复执行结果一致，无重复报告 |
| P4-05 | 同一秒多笔平仓 | 连亏与统计不漏单、不重复 |
| P4-06 | 离线期间无持仓 | 当前日状态精确恢复并允许开仓 |
| P4-07 | 离线期间存在持仓 | 明确标记峰值不可验证，进入保守恢复 |
| P4-08 | 缺少逐票状态的趋势单已部分减仓 | 不重复减仓 |
| P4-09 | 缺少逐票状态的超时剥头皮单 | 启动瞬间不意外强平，等待确认 |
| P4-10 | 历史未下载或 `HistorySelect` 失败 | 禁止开仓、允许平仓，并自动重试 |
| P4-11 | 周中跨日多次且 EA 未运行 | 周进度仍按自然周历史正确计算 |
| P4-12 | 重复实例 | 只有租约持有者执行恢复和补做 |
| P4-13 | 手动重置后重启 | 手动统计起点保持，不回退到日重置点 |
| P4-14 | 状态文件损坏 | 保留原文件，进入失败模式，不以零值覆盖 |
| P4-15 | 编译与交易回归 | 0 errors、0 warnings；下单、平仓及第三项状态无回归 |
